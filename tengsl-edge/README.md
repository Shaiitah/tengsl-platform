# TENGSL Edge Agent

Опрашивает по Modbus состояния зон/шлейфов через прибор-шлюз (например,
С2000-ПП в режиме Master) и публикует изменения состояния в MQTT в виде
нормализованных JSON-событий.

## ⚠️ Перед использованием на реальном объекте

- **Формула адреса регистра и таблица кодов событий взяты из официального
  руководства по эксплуатации** «С2000-ПП» (АЦДР.426469.020 РЭп, Изм.17 от
  21.08.2025), раздел 1.1.5 и таблица 1.1.5.12.1 — это не догадки.
  Но конкретное **сопоставление "№ зоны Modbus → физический извещатель"**
  для твоего объекта задаётся в UPROG (страница «Устройства» → «Таблица
  зон») и уникально для каждой инсталляции — сверь номера зон и адреса
  приборов в `config.yaml` с настройками твоего конкретного «С2000-ПП»
  перед запуском в проде.
- Классификация кодов событий по категориям `event_type`
  (normal/alarm/attention/fault/disabled/unknown) в `status_codes` —
  это наша собственная группировка кодов Bolid для окраски дашборда,
  не часть документации производителя. Таблица покрывает основные коды
  для адресных извещателей и состояния контроллера — если в системе
  появятся другие типы зон (реле, счётчики, РИП), в таблицу 1.1.5.12.1
  руководства нужно будет добавить недостающие коды.
- Настрой TLS и авторизацию на MQTT-брокере перед выходом за пределы
  локального теста — `docker-compose.yml` в этом репозитории использует
  Mosquitto без шифрования только для локальной отладки.
- Протестируй чтение регистров вручную (см. раздел "Проверка вручную" ниже)
  прежде чем доверять сервису автоматическую работу — особенно важно
  спровоцировать реальное тестовое срабатывание и убедиться, что событие
  приходит с ожидаемым `event_type`.

## Структура проекта

```
tengsl-edge/
├── app/
│   ├── config.py           # загрузка и валидация config.yaml
│   ├── modbus_reader.py    # чтение регистров через pymodbus (async)
│   ├── state_tracker.py    # отслеживание изменений состояния зон
│   ├── mqtt_publisher.py   # публикация событий в MQTT (aiomqtt)
│   └── main.py             # цикл опроса, точка входа
├── config.example.yaml     # шаблон конфигурации — скопируй в config.yaml
├── requirements.txt
├── Dockerfile
├── docker-compose.yml       # локальный тестовый стенд (agent + Mosquitto)
└── mosquitto.conf
```

## Быстрый старт (локально, без Docker)

```bash
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt

cp config.example.yaml config.yaml
# отредактируй config.yaml: адрес Modbus-шлюза, зоны, MQTT-брокер

python -m app.main --config config.yaml -v
```

Флаг `-v` включает подробное логирование (DEBUG) — полезно на этапе отладки
адресов регистров.

## Быстрый старт (Docker)

```bash
cp config.example.yaml config.yaml
# отредактируй config.yaml — для локального теста укажи mqtt.host: mqtt-broker, mqtt.use_tls: false

docker compose up --build
```

## Проверка вручную (перед автоматизацией)

Прежде чем доверять сервису, убедись, что регистры читаются и меняются как
ожидается, вручную:

```python
from pymodbus.client import ModbusTcpClient

client = ModbusTcpClient('192.168.1.50', port=502)
client.connect()
result = client.read_holding_registers(address=40000, count=1, slave=1)
raw = result.registers[0]
high_byte = (raw >> 8) & 0xFF
low_byte = raw & 0xFF
print(f"raw={raw} high_byte={high_byte} low_byte={low_byte}")
client.close()
```

Спровоцируй реальное событие (например, поднеси тестовый источник дыма к
извещателю или переведи зону в тест) и проверь:
- значение регистра меняется;
- `high_byte` (более приоритетный код) соответствует ожидаемому коду из
  таблицы 1.1.5.12.1 руководства (например, `37` при срабатывании "Пожар");
- сними тестовое воздействие и убедись, что регистр возвращается к коду
  `24` (взят под контроль) или другому "нормальному" состоянию.

Только после этого переноси номер зоны в `config.yaml` и запускай агент
в автоматическом режиме.

## Формат события в MQTT

Топик: `{topic_prefix}/{object_id}/events`, например `tengsl/obj-001/events`.

```json
{
  "object_id": "obj-001",
  "zone_number": 1,
  "zone_name": "Извещатель у входа",
  "device_type": "С2000-ДИП34А",
  "register_address": 40000,
  "raw_value": 9496,
  "primary_code": 37,
  "secondary_code": 24,
  "event_type": "alarm",
  "label": "Пожар",
  "timestamp": "2026-09-05T14:32:10+00:00"
}
```

`raw_value` — полное содержимое регистра (2 байта). `primary_code` —
более приоритетный из двух кодов состояния (старший байт, или младший,
если старший пуст) — именно по нему определяется `event_type`/`label`.
`secondary_code` — второй по приоритету код, если он есть (для
диагностики, обычно не нужен для отображения).

Статус самого агента (online/offline/starting/stopped) публикуется отдельно
в `{topic_prefix}/{object_id}/agent_status` с флагом `retain`, чтобы backend
сразу видел последнее известное состояние агента при подключении.

## Что дальше

- На стороне backend: подписаться на `tengsl/+/events` и `tengsl/+/agent_status`,
  писать в БД (PostgreSQL), поднимать WebSocket для дашборда тревог в реальном
  времени.
- Добавить health-check эндпоинт или `docker healthcheck`, если будешь
  разворачивать через оркестратор с автоперезапуском.
- Если объектов станет много — вынести конфигурацию зон в БД/API вместо
  YAML-файла на диске, чтобы не пересобирать образ при каждом изменении.
